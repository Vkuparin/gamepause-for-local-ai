# GamePause v0.3.0 review and v0.3.5 stabilisation plan

**Date:** 2026-10-04  
**Reviewed baseline:** branch `v0.3.0`, commit `7d4d184` (`P1-4: owner-drawn games listbox with per-game status dots`), package version `0.3.0`.  
**Scope:** independent code review and review of Kynsi's original assessment against `v0.3.0-update-plan.md`. This document supersedes the original verdict; its finding IDs are retained in the disposition table below. No implementation, version bump, commit, push, tag, or release is part of this pass.  
**Verdict:** the project builds and its current tests pass, but v0.3.0 is not yet a sound stabilisation baseline. Release panic containment is disabled by the build profile, round-trip verification bypasses durable recovery, and diagnostic/CLI paths do not consistently apply the monitor's safety rules. Fix the release blockers below before publishing the v0.3.5 bugfix/stabilisation pre-release.

The retained positive findings are meaningful: atomic JSON replacement uses flush plus `MoveFileExW`; normal pause persists intent before unload; partial normal restore retains staged recovery; identifier/variant/config verification prevents silently accepting a different instance; automatic-pausing-off retains pending recovery; restore-error labelling is correctly consumed by `attempt`; discovery retains per-adapter successful inventories; process caching uses PID plus creation time. ## Actionable findings

Priority: **P1** = release blocker involving loss of recoverability, process survival, or game-safety guarantees. **P2** = functional stabilisation work. **P3** = optional efficiency/cleanup. These are priorities for this pre-release, not claims that every scenario has been live-reproduced.

### R-1 — P1: release builds abort before discovery panic recovery can run

**Evidence:** `Cargo.toml:25` sets `[profile.release] panic = "abort"`; `discovery.rs:219-244` relies on `catch_unwind`; `scripts/build_release.ps1` builds with `--release`. A discovery panic terminates the process rather than returning retained inventory. The global hook can log first, but cannot keep monitoring alive. This contradicts the changelog and original P0-2 verdict. [Rust's catch_unwind documentation](https://doc.rust-lang.org/std/panic/fn.catch_unwind.html) explicitly limits catching to unwinding panics.

**Plan:** use an unwind strategy for shipped code if retaining catch-based containment. Keep the catch boundary on the discovery worker. Audit panic paths in `extern "system"` callbacks separately: changing the profile does not permit unwinding across Win32 callback boundaries. Bound recursive/input-heavy parsers so stack exhaustion is not treated as a catchable error.

**Acceptance:** a separate process built with the production release profile injects a discovery panic, remains alive, retains the last-good inventory, logs the failure, and successfully services a later refresh. Normal Cargo unit tests, including `cargo test --release`, do not alone establish the executable's panic strategy. Do not add a user-facing crash switch.

### R-2 — P1: round-trip verify can strand models without a recovery journal

**Evidence:** `engine.rs:297-440`. All models are captured and unloaded before restoration. Early returns after a second-model unload failure, a `loaded()` failure, a nonempty inventory, or a restore failure abandon the remaining work. There is no persistent snapshot for this operation. A crash after the first unload has the same outcome. `Engine::verify_round_trip` bypasses `self.state`; CLI verify also bypasses `Engine::new` (`app.rs:241-275`). The ordinary recovery mechanism cannot recover those models.

**Plan:** keep the intended round-trip feature, but execute its mutation through a durable, staged recovery transaction. Persist before the first unload; retain every unresolved model and server transition after failure; attempt recovery of all affected models rather than stopping cleanup at the first error; report original and cleanup failures separately. Respect game cancellation during recovery. Refuse to overwrite an existing or unreadable journal. Do not label a read-only config comparison as an equivalent round-trip test.

**Acceptance:** two-model tests fail each unload, inventory read, restore, field-read and final persistence boundary; every affected model is either verified restored or represented in valid persisted recovery. Restart a new engine after each destructive stage and resume. Verify must never replace a pending gaming journal. UI/report shows recovery pending and exposes retry. Include a CLI integration test, not only formatter tests.

### R-3 — P1: verify omits the server lifecycle needed to restore models

**Evidence:** `lmstudio.rs:497-527` starts then closes a temporary server when loaded models exist but HTTP was initially off. `verify_backend` then unloads and calls `backend.restore` without `start_server`. The real restore requires native REST and/or WebSocket access (`lmstudio.rs:232-312,543-559`). With the server initially off, verify can capture successfully, unload models, and then fail to restore them. The fake backend does not require a running server, so its passing test misses this dependency. The `verify-stopped` step means *inventory empty*, not server stopped; it is skipped altogether when the original server was off.

**Plan:** share the safe lifecycle with normal recovery: ensure control access while restoring and comparing, and return the server to its original running/stopped state only after recovery succeeds. Probe availability to avoid unnecessarily starting an already-running server. Do not apply original F-3's `server_stopped`-only gate. Rename the step to `verify-unloaded` or similarly accurate wording and perform that check for both initial server states.

**Acceptance:** backend fake fails REST/WS operations when stopped. Test initially running and stopped servers, zero/one/multiple models, nondefault port, start/stop failure, and retry. Preserve original server state and journal on all unresolved outcomes. Later live smoke tests must confirm the installed `lms server start` semantics rather than speculate about restarts.

### R-4 — P1: verify ignores observation mode, pending recovery, and running games

**Evidence:** `app.rs:486-494` calls verify unconditionally; dashboard `dashboard.rs:1330-1334` and tray `tray.rs:430` send it without the restore gates. CLI verify executes before journal validation. During observe mode it still unloads models. During a game or manual pause it can reload models that another client loaded, consuming VRAM while pausing is supposed to hold. The long synchronous worker operation prevents regular game polling; no cancellation callback runs between models.

**Plan:** enforce guards inside the action/transaction layer, with corresponding disabled controls and explanatory feedback: observe mode, pending recovery, active/manual pause, discovery not ready, corrupt journal, and operation already in progress. Scan immediately before mutation and between steps; cancel further loads if a game starts, preserving recovery. Make the disruptive nature explicit at invocation. CLI uses the same rules, with explicit nonzero refusal.

**Acceptance:** all guarded states issue zero unload/load commands; a game appearing mid-operation stops further loads and retains recovery. Repeated clicks cannot queue multiple destructive runs. GUI and CLI obey the same contract.

### R-5 — P1: CLI restore drops the remembered-game and exclusion safety guard

**Evidence:** `app.rs:319-336` scans fresh discovery using the normal configuration. It does not merge `engine.remembered_games` and does not clear `excluded_paths` / `excluded_executables`. The GUI restore does both (`app.rs:473-482`); the automatic path also uses an exclusion-free recovery scanner. After registering a custom game, pausing, removing/ignoring its path, and restarting, CLI `--restore` can miss the still-running game and restore into its VRAM budget.

**Plan:** centralise the recovery game-set and scanner policy and reuse it for GUI, automatic, and CLI restoration. Fail closed on scan errors. Distinguish a cancelled/deferred restore from completed restoration in CLI output and exit status.

**Acceptance:** persisted custom-game recovery remains protected after removal/exclusion and a restart. Exercise both the initial CLI guard and cancellation between models using an injectable scanner. No load occurs while the remembered game is running.

### R-6 — P2: CLI verify can silently succeed without running when the GUI is open

**Evidence:** the instance-lock failure branch (`app.rs:211-224`) excludes doctor/discover/restore but omits `args.verify`. With a running GUI and default CLI flags, `GamePauseCLI.exe --verify` can open the existing dashboard and return `Ok(())`, yielding no verify report and exit code zero.

**Plan:** either explicitly reject verify while the GUI owns the data directory, or route to a deliberate request/response mechanism that returns the result. For v0.3.5, a clear nonzero busy error is sufficient. Do not bypass locking to mutate models concurrently. Reject conflicting one-shot CLI modes rather than silently choosing the first.

**Acceptance:** invoke the real CLI while a test process holds the lock; require a report from an actual run or nonzero error. Zero exit with no operation is forbidden.

### R-7 — P2: claimed per-capture/restore WS logging is absent from normal use

**Evidence:** all production calls to `ws_log` are in CLI verify's post-run loop (`app.rs:263-265`). Normal capture/restore, dashboard/tray verify, `raw_config`, and `load_model` have no such calls. CLI verify logs aggregate stages with `lms version`, not each WS operation or an independently established LM Studio server version. A crash mid-operation leaves none of these lines. Helper tests validate formatting and the sink, not production instrumentation.

**Plan:** connect a best-effort local logging context to actual WS boundaries for all entry points; identify operation/model, actual known version source, outcome and differing field. Cache version information rather than spawning once per field. Never log passkeys, API tokens or full sensitive payloads. If only CLI version is available, label it accurately.

**Acceptance:** capture/restore tests using an injected transport and log sink produce the expected records through real call paths, including failure mid-load and GUI invocation. Logging failure does not change operation results. Update changelog/docs to match actual coverage.

### R-8 — P2: doctor fails before it can report the conditions it should diagnose

**Evidence:** `app.rs:285-315` propagates backend creation and snapshot errors before assembling diagnostics. Missing CLI, busy inference, native API failure, WS incompatibility or unavailable data directory can therefore prevent a structured report. `diagnostics` (`lmstudio.rs:411-438`) has no WS protocol result; there is no dashboard diagnostics view. The writability test uses a file as the directory, not a genuine read-only directory.

**Plan:** make probes independent and return per-probe success/error/unknown. Keep doctor free of model unloading and disclose any temporary server change. Include explicit CLI, server, loaded inventory, WS compatibility and writability outcomes. Provide the planned dashboard view or explicitly defer it and correct the panel claim; a bugfix release need not grow a new UI silently. Report unavailable versions rather than discarding the remaining diagnostics.

**Acceptance:** structured useful output for missing CLI, busy AI, HTTP/WS failure, no models, and unwritable directory; remaining probes still run when one fails. Validate actual read-only access where feasible. No model load/unload occurs.

### R-9 — P2: state classification announces restoration before it happens

**Evidence:** `tray.rs:318-329` treats only `AI paused...` or manual pause as Paused; `Restoring AI in 30s` maps to Idle. The timer (`tray.rs:535-549`) toasts/beeps on any kind transition. Consequently automatic pause -> grace countdown emits a success toast/sound and healthy icon while models remain unloaded. Subsequent `AI restored` is also Idle, so the actual completion may emit no toast. Error -> countdown/other idle messages has a similar false success path. Sound is unconditional in `state_toast`; no optional-sound setting exists despite the changelog wording.

**Plan:** separate visible pending/restoring state from operation-completion notifications, preferably with typed shared state/events rather than string-prefix parsing. Emit restore success only after verified completion and final journal persistence. Correct the optional-sound claim or deliberately add a preference within agreed scope.

**Acceptance:** pause -> grace -> restore success produces exactly one pause and one restore-completed notification; countdown, cancellation, error retry, detection-off and startup do not emit false completion. Pending recovery never gets a healthy-restored indicator merely because a countdown starts.

### R-10 — P2: DPI relayout scales geometry but leaves fonts and fixed list rows unchanged

**Evidence:** `dashboard.rs:538-572` moves controls on DPI change; the font is created once at `dashboard.rs:1544` and never replaced by relayout. Owner-drawn fixed row height is set during `WM_MEASUREITEM`, with no `LB_SETITEMHEIGHT` on later DPI changes. Dot/text offsets in `draw_list_item` are literal pixels. `WM_DPICHANGED` ignores its recommended rectangle. Scaling helpers passing at 100/150/200% does not establish consistent live text/row scaling.

**Plan:** rescale/recreate the shared font, update fixed item height and drawing offsets, preserve selection and scroll, handle the recommended window bounds, and dispose old GDI resources after replacing them.

**Acceptance:** production dashboard moved between 100/150/200% monitors retains readable proportionate text and rows, usable controls, and selection; repeated moves do not grow GDI handle counts. Record live evidence separately from helper tests. Check work-area fit at high DPI.

### R-11 — P2: full dark-theme support is not established by the current implementation

**Evidence:** `tray.rs:220-247` reads `ColorsUseLightTheme` with a light fallback and applies DWM once at creation. No theme-change handling exists. Dashboard painting uses classic `GetSysColor` values (`dashboard.rs:1441-1450`) without an app-dark palette; passing tests merely check the chosen color index. The test reading the preference twice cannot establish it is the correct app theme signal. A dark title bar alone does not theme the client area. [Microsoft's Win32 theme guidance](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/ui/apply-windows-themes) separates theme detection, change tracking, title-bar support and client-area painting.

**Plan:** use a verified app-theme signal; handle changes while the window remains open; align background, static/edit/list/button text and selection colors with the active palette while respecting high contrast. Retain native controls and existing dependencies where practical. If full support is deferred, narrow the release claim explicitly.

**Acceptance:** inspect light, dark, independently configured app/system themes, and high contrast in the actual dashboard; toggle theme while open. Show readable consistent client and caption colors, not only a non-panicking DWM call. Live appearance remains unverified in this review.

### R-12 — P2: communication waits are not bounded end to end

**Evidence:** `lmstudio.rs:211-231,314-325` loops over WS messages without a total deadline. Read timeouts apply to individual blocking reads, so continuing unrelated messages/pings can keep capture/read-back alive indefinitely. `load_model` checks a 300 s clock before a potentially 180 s read, and `receive` can itself keep looping on control frames. In `run_command` (`lmstudio.rs:563-604`), timeout covers waiting for the direct child, then pipe reader joins are unbounded; a descendant retaining inherited pipe handles can keep them blocked after the parent exits. The 4 MiB cap also stops reading each stream; it does not keep draining excess output as the old review claimed.

**Plan:** enforce an operation-wide deadline across receive loops, use remaining time for reads, and make subprocess capture/reader completion bounded including inherited-handle cases. Drain excess output while retaining only a bounded prefix and mark truncation. Keep this scoped to liveness, not a protocol rewrite.

**Acceptance:** injected peers continuously emit unrelated frames/pings without a valid result, and a helper child exits while a descendant holds a pipe; operations return within the specified bound. Test output exceeding the cap. Worker remains able to service quit/recovery afterward.

### R-13 — P2: status files are treated as evidence of a currently running app

**Evidence:** `app.rs:159-180` reads cached files with no liveness/freshness check; every read error becomes `absent`, including permission/I/O errors. `status.json` survives quit/crash and is updated only when its content changes. `docs/USAGE.md:48` promises absent output when the app is not running, which is not what stale files do. Status strings/game names are not escaped for their advertised line-oriented output.

**Plan:** define cached-state versus current-running-state semantics explicitly. Use a real liveness check or appropriate freshness metadata for status; keep a separate cached inventory concept. Return absent only for NotFound; surface other I/O errors. Escape tab/newline delimiters or offer a documented JSON output form for scripts.

**Acceptance:** cover running-but-idle, exited/crashed, missing file, access denied, corrupt JSON, and names/errors containing tabs/newlines. Integration tests must use the actual status payload (whose `active_games` is an array) as well as fixture shapes.

## v0.3.5 implementation order

This is the proposed work queue, not implementation approval or a release instruction. Keep the scope to bugfixes, resilience, truthful diagnostics and completion of promised behaviour; defer broader architecture and cosmetic work. Preserve schema-2 journals and configuration migration. If diagnostic transaction metadata needs an extension, document backwards compatibility before implementing it; do not repurpose or overwrite existing recovery.

1. **Release resilience:** R-1; add the production-profile subprocess regression. Audit callback panic boundaries and parser bounds.
2. **Safe shared recovery:** R-2/R-3/R-4/R-5 together. Give verify a durable transaction, implement server lifecycle and guards, and reuse the recovery scanner policy. Build failure/cancellation/restart tests before UI integration.
3. **CLI correctness and diagnostics:** R-6/R-7/R-8/R-12/R-13. Prefer small changes that make failures explicit and bounded; record any intentionally deferred diagnostics panel.
4. **Trustworthy UI:** R-9, then R-10/R-11. Completion events first; DPI/theme validation next. Theme claims must be narrowed if full client-area support is deferred.
5. **Documentation and packaging:** reconcile README's `0.2.0 preview` wording, installer fallback `0.2.0`, misleading optional-sound/doctor-panel/per-WS-log claims, CLI semantics, verify safety and validation evidence. Keep older benchmark results explicitly labelled v0.2.0 rather than relabelling them. The fallback installer version is stale, although the build script overrides it correctly. Avoid shipping internal review/plan documents accidentally: the build script copies every `docs/*` file. Decide intentionally what belongs in the user bundle. Update Cargo.toml/Cargo.lock/changelog to the chosen v0.3.5 pre-release version consistently when implementation is ready.
6. **Optional P3:** original F-2 inventory-call optimisation and F-4/F-6 cleanup only after correctness regressions are locked down. No new launcher/features/framework/dependencies or benchmark claims needed for this patch.

- [ ] Locked test/fmt/Clippy/release build pass on pinned Rust; production-profile panic subprocess and failure-injection tests pass.
- [ ] Interactive popup reentry test passes on an interactive Windows desktop (already passed at this baseline; rerun if that path changes).
