# GamePause v1.0.0 provider and UX design

Date: 2026-10-04. Baseline: `dc29db8`, package 0.3.5. Status: executable release specification, followed by design rationale. Based on the owner's [playtest notes](../playtest_notes.md) and design interview. The [implementation tickets](../v1.0.0-update-plan.md) assign this work. Interview decisions govern behavior; implementation types, timing and budgets remain proposals where labelled. This specification does not authorize implementation or publication.

## Task brief

### Objective

Release a dependable, lightweight native Windows GamePause that automatically makes room for games and restores local AI afterward. Users must understand detected games, enabled-provider state, reasons, next transitions and available actions without consulting logs or Advanced settings. Preserve existing LM Studio restoration fidelity and prepare experimental opt-in Ollama pause/restore for the evidence-supported subset.

### Deliverables

Implement the behaviors R1-R10 below across the Rust worker, native dashboard/tray, validated settings and recovery. Deliver the existing installer/portable formats, CLI compatibility, updated user/developer documentation and version-specific acceptance evidence. This document specifies the future implementation; the current assignment produces only this specification and the local ticket plan.

Follow [CONTRIBUTING](../CONTRIBUTING.md), [Development](DEVELOPMENT.md) and the current AGENTS instructions. Keep Rust, windows-sys and native controls, window handles on the UI thread and engine control on the worker side. Release locks/borrows before message-dispatching Win32 calls. Reuse existing dependencies; no new runtime dependency is planned. Keep loopback control, bounded timeouts/output/idle work, incremental discovery and atomic persistence. Preserve executable names, installer identity, startup/data paths and existing explicit preferences.

Build packaging tools and existing bounded Xbox discovery subprocesses are distinct from the application's Rust runtime. Do not commit, tag, push or publish without a request.

## Core UX requirement: make program state understandable

Intuitive state information is a core requirement of the whole app, not optional dashboard polish. Without opening Advanced settings, logs or a tooltip, the user should understand which games are detected, what each enabled AI provider is doing, why it is doing it, what will happen next, and which actions are available. The tray must communicate the same facts concisely.

Separate current state, requested work and confirmed results. A click acknowledged is not an operation completed. Pending recovery is not proof that AI is paused. Automation enabled is not proof that a provider is reachable. Unknown or stale provider evidence must stay visibly unknown or stale. Partial provider outcomes must never become a global success message.

Put concise state and reason together, with timing where meaningful and an action when intervention is needed. Examples below describe behavior, not a fixed wording contract:

| Situation | Information the user needs |
| --- | --- |
| Watching | No recognized game running; enabled providers available/unavailable; automatic pausing on/off |
| Busy inference | Game name; provider waiting for active work; resources not yet released |
| Unloading | Provider and operation in progress; no completed-pause claim yet |
| Completed pause | Detected game names; confirmed provider/model/server outcomes |
| Restore countdown | Models still paused; time remaining; another game cancels the countdown |
| Restoring | Provider being restored; completion not yet verified; remaining work |
| Confirmed gameplay override | AI running/restoring during gaming by the user's choice; normal pausing resumes for another nonignored game or after restart |
| Partial failure | Which provider succeeded, which failed, what recovery remains and the next useful action |
| Unknown/unavailable evidence | What could not be checked; no claim that AI is safely paused or restored |

Core Pause and Restore remain visible. Central status names enabled providers, including simultaneous LM Studio and Ollama use. Disabled Ollama has no redundant row or message. Disabling any provider is blocked while recovery is pending, with its current state and the required recovery action explained. Ordinary provider configuration and diagnostics remain advanced tools.

Use text and hierarchy as the primary explanation; color supports it. Keep the summary stable between meaningful state changes, and preserve feedback long enough to read. Progress animations or more polling are not substitutes for factual state. Each command and transition must update the shared state model, GUI, tray availability and feedback consistently.

Preserve that lifecycle and low overhead. These are owner observations, not instrumented performance results or proof of complete restoration fidelity. Most reported problems concern information hierarchy, native drawing, action availability and feedback. The default dashboard should answer two questions immediately: which games GamePause sees running, and what state the AI is in. ## 1. What provider-agnostic means here

GamePause should own game detection, grace periods, recovery intent, retry scheduling and status. Each provider adapter should own model identity, snapshot completeness, unload/load operations, verification and any server control it can safely support.

Use a small compiled set of adapters. A trait and an enum of typed snapshots are enough for two initial providers. Dynamic plugins, SDK dependencies and a universal inference client would add machinery without solving lifecycle differences.

The existing `Backend` trait is useful groundwork, but `Model` requires LM identifiers, base keys, namespaces and raw load fields; `Snapshot` assumes LM server state; engine validation and loaded-model matching also know those fields. Move that knowledge into the LM adapter. Preserve its detailed capture behavior and tests.

## 2. Provider feasibility

| Provider | Proposed support | Main issue | Effort judgment |
| --- | --- | --- | --- |
| LM Studio | Stable target; retain full currently captured settings verification | Internal WS compatibility remains a maintenance dependency | Moderate refactor risk; strongest existing evidence |
| Ollama | Experimental target, off by default; no live validation | Live options/expiry ambiguity, unload completion and external reload | Source/fixture implementation; community completion welcome |
| Other local runtimes, including llama.cpp | Outside the agreed scope; no scheduled work | Require their own lifecycle and validation contracts | Not estimated |
| Remote/cloud inference | Outside 1.0 scope | Pausing usually releases no local model memory | Little value for the core feature |

These are engineering judgments, not a ranking of provider usage. LM Studio and Ollama are a focused initial choice; no popularity claim is required.

Ollama documents resident inventory at `GET /api/ps`, including model identity, digest, expiry, VRAM size and context length. That is a useful snapshot surface, but not a dump of every live load option. [Ollama resident inventory](https://docs.ollama.com/api/ps).

Ollama documents empty requests for preloading and `keep_alive: 0` for unloading. Its default endpoint is loopback port 11434. These controls do not establish a durable block on future client requests. [Ollama FAQ](https://docs.ollama.com/faq).

Upstream source currently routes an empty generate unload request to scheduler expiration. The scheduler uses reference counts to defer expiration while work is active. Inference: this may provide safe deferred unloading without a public idle flag. It is implementation evidence, not a stable API promise. Inspect and test the chosen release; never report completion just because the request returned successfully. [Ollama request handler](https://github.com/ollama/ollama/blob/main/server/routes.go), [Ollama scheduler](https://github.com/ollama/ollama/blob/main/server/sched.go).

The current public resident response type does not expose all active runner options or an active-request count. Absence of that data must become an explicit unknown capability. [Ollama API types](https://github.com/ollama/ollama/blob/main/api/types.go).

Ollama also exposes an embedding endpoint. Preload/unload behavior for embedding-only models needs separate fixtures and live validation; a chat-only implementation must not claim embedding parity. [Embedding API](https://docs.ollama.com/api/embed).

Prior research found llama.cpp router lifecycle endpoints, but this does not add it to the roadmap. Provider expansion for 1.0 stops at experimental Ollama. [Prior research reference](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).

LM Studio's public v1 API has load/unload operations and exposes several load fields. Compare those fields with current raw snapshots before replacing internal WS calls; fewer transport paths are useful only if settings preservation survives. [REST overview](https://lmstudio.ai/docs/developer/rest), [load API](https://lmstudio.ai/docs/developer/rest/load), [model inventory](https://lmstudio.ai/docs/developer/rest/list).

All links were checked on 2026-10-04. Moving documentation/source branches are research references, not the release compatibility matrix. Pin upstream commits and exact executable versions when implementation begins.

## 3. Provider contract

Proposed concepts:

| Type | Meaning |
| --- | --- |
| `ProviderId` | Stable configured instance ID, such as `lmstudio-default`; distinct from provider kind |
| `ProviderKind` | LM Studio or Ollama; compiled adapter choice |
| `ProviderCapabilities` | Capture fidelity, model types, verification fields, safe unload mode, server control and reload prevention |
| `ProviderHealth` | Available, unavailable, incompatible, or unknown, with bounded diagnostic detail |
| `ActivityState` | Idle, busy, or unknown; unknown is never silently converted to idle |
| `ProviderSnapshot` | Tagged, versioned LM Studio or Ollama payload; common core does not interpret raw provider config |
| `VerificationResult` | Passed promised fields, deferred, failed, or unsupported; includes which guarantee was checked |
| `ProviderProgress` | Per-provider stages, errors and retry deadline |

Sketch of operations: `probe`, `capture`, `validate_snapshot`, `request_unload`, `verify_unloaded`, `restore_next`, and `verify_restored`. Capability-specific lifecycle hooks handle temporary control-server access, final server state and interruption. Exact signatures should follow the LM parity refactor rather than force working behavior into a speculative large trait.

Keep common capture headers for display and routing: provider ID/kind, resolved loopback endpoint, adapter payload version, compatibility evidence and guarantee. Keep identity and configuration in typed provider payloads. Retain LM raw JSON fields inside its payload to compare every currently captured key.

Adapters return factual results. The coordinator decides scheduling and persistence. An adapter must not erase recovery or silently downgrade its guarantee. A version string alone is insufficient proof of compatibility; validate required response structure before unloading.

Errors need enough structure to distinguish unavailable/retryable, busy/deferred, incompatible, persistence failure and identity/settings mismatch. Existing readable error messages should survive; avoid branching exclusively on error strings.

## 4. Restoration guarantees

| Guarantee | Required behavior | Initial application |
| --- | --- | --- |
| Captured settings verified | Restore identity and all fields currently captured by that adapter; compare read-back | LM Studio, preserving current behavior |
| Supported fields verified | Restore identity plus an explicit limited field set; disclose uncaptured state before enabling | Experimental Ollama policy; runtime checks and fixtures do not establish live compatibility |
| Monitor only | Show detection/diagnostics; never unload or load | Unsupported versions, unresolved capabilities or user-disabled control |

Ollama stays experimental even if fixture tests pass. Its UI, CLI and docs must identify unimplemented behavior and the lack of live validation. Opt-in does not bypass capture, journal, identity or game guards; operations whose safety contract remains unresolved are unavailable or monitor-only. Stable LM Studio release acceptance does not depend on completing Ollama. Do not call Ollama restoration exact if only identity and context can be verified. Neither provider should promise conversation/KV-cache preservation; reloading a model is not resuming an in-flight response.

Proposed Ollama payload: canonical local name, digest, model capabilities/type, observed context, raw expiry evidence, chosen expiry policy and any replayable supported fields. Model names are routing hints; digest is identity evidence. Recheck local catalog identity before loading. If the name now identifies different content, retain recovery and show the mismatch. Do not download, silently substitute, or assume a digest is itself accepted as a load identifier.

Context length must be characterized before replaying `num_ctx`: concurrency and version behavior may affect how inventory describes effective allocation. Tests must establish the mapping rather than assume the displayed number is the per-request option.

Expiry is a policy decision. A timestamp does not reconstruct the original `keep_alive` setting reliably, particularly during active inference or indefinite residency. The spike should compare preserving remaining observed residency after restore versus honoring the original absolute deadline. Never turn a finite/unknown expiry into indefinite residency. Store the chosen policy in recovery so changed settings cannot reinterpret an old transaction. If the absolute-deadline policy intentionally skips expired models, report that outcome separately from restored models.

Multiple models are another contract check: a later preload can evict an earlier one. Final verification must assess the promised set, not only each load's immediate success. Unstable residency must not create an unlimited restore/evict loop.

## 5. Session and recovery

Proposed schema-3 journal structure:

```text
schema: 3
session: remembered games and common pause/restore intent
providers:
  provider ID, kind, endpoint, captured guarantee/policy
  versioned provider snapshot
  provider lifecycle intent and completion
  per-model planned/unloading/unloaded/restoring/restored progress
```

This is a shape sketch, not a serialization specification. Retries use monotonic runtime deadlines; persisted stages reconstruct safe work after restart. Expiry timestamps, where needed, remain provider payload data with explicit clock-change handling.

Rules:

1. Capture and validate a provider's complete supported snapshot, then atomically persist it before any unload or lifecycle mutation. LM's existing temporary capture-server behavior must retain cleanup guarantees; failure to close it is surfaced.
2. Add providers independently to the shared transaction. A capture failure for Ollama need not block a valid LM pause, but the UI must say protection is partial.
3. Mark unload complete only after confirming the captured instances are absent. Keep delayed/busy unloading pending. Persist restore intent before loading.
4. Scan games before each restore unit and between units. Automatic recovery remains game-guarded. Confirmed gameplay restoration may exempt only the live game instances approved by the user; another nonignored game revokes that exemption. In-flight loads may not be instantly cancellable; reconcile their completion and repause when needed. Snapshot originals are never replaced with an intermediate inventory.
5. Restore providers/models serially to avoid concurrent VRAM allocation bursts. Continue healthy providers after another provider fails, with separate bounded retry state.
6. A provider completes only when its promised restore and lifecycle checks pass. Clear the journal only after all entries are complete and clearing is persisted. Never delete unresolved entries to obtain a green status.
7. Disabling automation retains recovery obligations. Reject disabling or removing a provider while its recovery is pending and explain the state/required action; do not silently hide an obligation. Observation mode remains non-mutating. Changing endpoints during recovery is rejected or deferred; recovery routes to its captured instance, not a newly selected provider.
8. Missing provider on restart keeps recovery pending and explains how to retry. Unknown schema/payload versions fail closed. A failed migration never overwrites the only authoritative journal.

Schema-2 migration maps only to LM Studio, preserves every old field/stage, and uses the recorded port/server intent. Settings migration maps existing `lms_path`, `api_host` and server-stop preference into the LM entry. Preserve games, exclusions, delays, automation choices, and startup paths. Provider IDs survive display-name changes.

The first release can support one configured endpoint per kind while retaining stable instance IDs. Arbitrary multiple instances and automatic endpoint remapping are later work. Prevent two IDs or two active data directories from controlling the same endpoint; the existing data-directory lock alone does not establish endpoint ownership. Resolve cross-instance locking and CLI participation in P0-4 before claiming safe simultaneous control.

## 6. Automation and resource cost

Probe known/configured loopback endpoints on startup, explicit refresh and bounded unavailable retries. Use installation hints only as hints. No port sweep, recursive provider-directory scan, automatic process launch or frequent provider CLI polling. Validate provider-native responses rather than classify a service from an open port.

Detect new provider installations through a low-frequency discovery check or explicit refresh; never automatically enroll a newly detected provider in a limited guarantee. Enabling Ollama should be one local choice with concise experimental/unverified disclosure, not JSON editing or permanent model selection. Keep it off by default.

Retain one game scan and inventory worker. A small fixed adapter set can use enum dispatch; trait dispatch is also negligible relative to IPC. The significant costs are provider probes, subprocesses, state writes, drawing and time spent blocking the control owner.

Bound response sizes, connect/read/operation deadlines and retry rates. Perform only a bounded amount of provider work before servicing process checks. Current synchronous operations mean a scan-latency budget cannot be assumed; prove it with slow fixtures and use a bounded Rust control worker if necessary. Keep windows on the UI thread regardless of that result.

After a completed LM pause, keep its current quiet behavior. Ollama's running service can accept another client request. If limited residency checks are included, they should detect and report renewed loading with bounded frequency. Do not repeatedly fight clients, accumulate new models into the original snapshot, or claim sustained resource protection from a one-time unload. Endpoint shutdown, process termination and request proxying are outside the initial adapter contract.

Prefer honest states such as "Models unloaded; clients can reload" and "Waiting for AI to finish". Continuous agents may prevent resource release. Do not claim bytes of VRAM freed from a model's file size; provider memory estimates, if displayed, need explicit labels.

Keep provider controls, logs, diagnostics, disruptive tests and advanced connection/delay/notification settings out of that view. Remove game-row dots, while preserving the useful tray state colors and text.

### Layout, drawing and interaction

Use native tab/navigation controls for Games, Running apps and Ignored, with a visible selected page and accessible keyboard behavior. Action buttons remain visibly distinct. Use a consistent spacing grid, resize rules, one owned palette/font/resource layer, and measured text plus padding to establish control widths at each DPI. Prefer short labels such as Remove selected and Test round-trip; a tooltip must not compensate for a clipped visible caption.

Add native tooltip controls for actions, toggles and advanced tools. Descriptions explain consequences and reasons for unavailability, including the fact that a round-trip unloads/reloads models. Expose equivalent descriptions to keyboard and assistive-technology users. Keep the app version visible without opening diagnostics, using the package build version rather than a hardcoded caption.

Selection must preserve readable text in focused/unfocused, selected/unselected, disabled and high-contrast states. The current owner-draw DC lacks an explicit text background mode; reproduce the reported white rectangle and set drawing state deliberately, restoring the DC afterward. A transparent text background over the painted row is one candidate. [Microsoft background-mode reference](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-setbkmode). Removing dots does not remove the need to test selection rendering.

Theme the entire client, including edit/list/button/tab/group backgrounds, selection, focus and disabled states, together with the caption. Follow system light/dark changes and high contrast. Keep native accessible controls and documented Win32/GDI customization. No new GUI stack, GPU renderer, animation loop or continuously repainted dashboard.

### Advanced settings and tray parity

Use a persisted `advanced_settings_visible` preference, default false. It is a presentation choice, separate from automation or provider enablement. Changing it updates the open dashboard and subsequent tray menus through validated settings/shared state. Hiding controls never stops an enabled provider or abandons recovery. Hidden controls leave the tab order; hidden commands also reject stale UI dispatch.

All provider configuration/status detail, diagnostics, test/verify actions, logs/status-folder actions and noncore settings belong here. Central AI status still shows failures and recovery actions for any enabled provider. Ollama stays experimental/off by default regardless of advanced visibility.

Proposed tray order: concise status; Open GamePause; separator; automatic-pausing toggle, Pause AI, Restore AI; separator; Refresh games; advanced-only tools group when enabled; separator; Quit. In the advanced group, put diagnostics and provider details before Test round-trip, logs/status folder and startup preferences. Drop the duplicate Settings and games route in favor of Open GamePause. Use exactly Quit; describe retained recovery in its GUI help/documentation rather than the menu caption.

Every actionable tray command has a GUI counterpart under the same visibility rule, including Open logs and status folder, startup preference and Quit. Both surfaces use the same command IDs/availability model and route to the same worker action. A tray-only advanced action must never be the only way to reach a tool.

### Pause and restore policy

Availability comes from typed worker status, not string-prefix matching or active mode alone. Share the policy between GUI and tray; revalidate on the worker because status can change while a menu/dialog is open.

| State | Pause action | Restore action |
| --- | --- | --- |
| Watching, active, no work pending | Available for a manual hold | Disabled if there is no recovery |
| Capturing, unloading, restoring or verifying | Disable duplicate/incompatible requests | Disable duplicate/incompatible requests |
| Completed pause while a game is running | Disabled: AI is already paused | Restore... opens the warning; explicit confirmation permits immediate restoration |
| Confirmed coexistence while games run | Pause AI can end the override and return to the normal pause path | Disabled if restoration is complete; Retry restore for unresolved recovery uses the still-valid scoped override |
| Manual hold with no games | Resume AI releases the hold and uses normal restore guards | Available when recovery and discovery permit |
| Recovery pending, games absent, discovery ready | No redundant pause; retry policy remains available where appropriate | Restore AI now or Retry restore |
| Observation, detection unavailable or corrupt recovery | No destructive action | Show why restoration is unavailable; retain recovery |

Gameplay restore confirmation names the detected games and warns that loading AI now could exceed available VRAM. Offer Cancel (default) or Restore AI now. Confirmation requests immediate restoration and creates a temporary coexistence override so the watcher does not immediately unload again. Automation remains configured on; the central summary explicitly states that pausing is temporarily overridden by the user's choice. Do not infer free memory or promise that restoration will fit. Keep journal-before-mutation and verified recovery through load failures.

The override applies only to the currently confirmed live game instances, using process-instance identity where available. Another recognized nonignored game, including a relaunched instance, cancels it and resumes normal pausing. It also ends when the confirmed games exit, the user chooses Pause, or GamePause restarts. Do not persist the authorization across restart, change global automation, or implicitly ignore games. After an in-flight load completes during revocation, reconcile and use the normal pause path; do not discard unfinished recovery. Failed/unknown detection refuses a new override and must not keep an exemption active on an unverified game set. Define a conservative reconciliation path in engine tests.

In the same confirmation, list currently running games with individual, initially unchecked Ignore in future selections. Persist only selected executable exclusions, never all games implicitly. Successful saves prevent future pause triggers from those games, but another nonignored game can still pause AI. Ignore alone, elsewhere in the UI, affects future triggers only and never authorizes current restoration. The current restore uses explicit confirmation even when exclusions were selected. Report exclusion-save success/failure separately from restoration; a failed save must not claim the preference was remembered. Preserve remembered-game recovery checks outside the scoped override.

Both dashboard and tray use this flow. Recheck current/remembered games, provider state and detection health after the dialog without holding a UI borrow or shared mutex during the native call. A new game appearing after confirmation is not silently approved. Ordinary Restore AI now clicked before a game starts still defers when the worker detects gaming; it has no override authorization. Stale/duplicate confirmations cannot broaden or recreate a revoked override.

Do not let Pause AI's old toggle behavior create a hidden manual hold when AI is already automatically paused. A manual hold is created/released through an explicit valid action. Completed pause and model/server claims require factual operation progress; pending recovery alone does not mean unloading finished.

### Feedback and selected-game operations

Every function has a visible result: immediate actions show their outcome; asynchronous requests show acknowledgement, busy state, completion/no-change or failure. Cancelled pickers/dialogs show cancellation without recording success. Refresh acknowledgement is not completion: attach a request ID/generation and complete only when the discovery result is accepted. Coalesce repeated refreshes and report that one is already in progress. Keep completion feedback until another user action or a higher-priority error replaces it; status timers must not overwrite it with the generic refresh hint or an old verify report.

Feedback stays inline for normal operations. Reserve a modal for a meaningful destructive confirmation or hard failure, not a successful refresh. Report open-folder/startup/config-save failures rather than accepting an action silently. Do not poll providers just to populate acknowledgement text.

Custom-game removal remains selected-only. Enable Remove selected only for a custom selection, identify the game in its hint/confirmation, and acknowledge the saved removal. Cancel leaves settings unchanged; failure to save must not optimistically remove the row. Launcher-discovered games use Ignore selected instead. Removing an active custom registration does not remove its remembered game from pending recovery checks.

Advanced provider details show endpoint, availability/version evidence, supported guarantee, known loaded state, last result and pending recovery. Ollama details explicitly say "Experimental. Not tested with a live Ollama installation," list known gaps, and offer opt-in only for implemented evidence-supported control. Add a contribution link when the feature lands. Advanced diagnostics show independent probes with time/staleness and concise next actions. If authentication is needed for supported LM versions, design local credential handling and redacted reporting before adding a password field; never place tokens in the journal/log.

### Sounds and notification delivery

Use one sound source per completion event. With notifications enabled, let Windows own the notification sound and remove the additional `MessageBeep`. Silent preference uses `NIIF_NOSOUND`. With visual notifications disabled but sound explicitly enabled, one standalone system sound may be used. [Microsoft notification flags](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-notifyicondataw). Fixing duplicate playback intentionally changes the current migration/default behavior; preserve existing explicit future user preferences, not the accidental double sound.

Try a short bounded success-notification delay, initially two seconds after confirmed completion, without delaying unload/restore work. Keep at most one queued success event per session; discard stale pause success if restoration has already started, and distinguish partial provider outcomes. Failures remain immediately visible in central/tray state. A delay may improve delivery during launch, but cannot promise visibility over fullscreen games or Windows notification suppression. Respect Windows settings/quiet time. Do not add a forced topmost window, focus stealing, game overlay or periodic redisplay to obtain visibility. Human acceptance should compare windowed/borderless/fullscreen and notification-suppressed behavior; the dashboard/tray remain the reliable persistent record.

## 8. What is missing most

The product already covers the essential game lifecycle. The next value comes from explaining state and finishing trust-related work:

- A central game/AI status and readable, state-aware actions.
- Full dark client rendering, readable selection, measured button sizing, useful hints and distinct navigation.
- An explicit Advanced settings checkbox with GUI/tray command parity and a read-only doctor view.
- Action acknowledgement/completion and clear partial/deferred recovery states.
- Single-source sounds, bounded notifications, keyboard navigation and high-contrast checks.
- Tested sleep/resume and provider-restart reconciliation.
- Release-candidate performance, live compatibility and upgrade evidence, rather than reused preview numbers.

Further provider work is unscheduled. Community contributions can complete experimental Ollama support and provide live evidence. Measured control-path reductions remain useful; preserve race checks when reducing inventory subprocesses, because a cached inventory is not proof that live state stayed unchanged.

## 9. Discussion points

The agreed direction is stable LM Studio and experimental Ollama. Intuitive state communication is core UX across the app; playtest-driven state/feedback fixes come first. Interview decisions authorize immediate confirmed gameplay restoration with a temporary override, per-game remember selections, core Pause/Restore, enabled-provider summaries, blocking provider disable during recovery, and slightly delayed Windows notifications with one sound source. Implementation is planned in hour-scale sessions; human acceptance remains separate. Settle the experimental field set, expiry policy, source/fixture inference-deferral evidence and external-client limitation. Ollama does not become stable without later live validation; notification visibility over every game is not guaranteed.

Keep the product name GamePause, existing `GamePause.exe`/`GamePauseCLI.exe`, installer identity and data directory. Update LM-specific marketing when another adapter is supported. Repository and Cargo package renaming can wait; it adds upgrade/tooling churn without improving the automatic workflow.
