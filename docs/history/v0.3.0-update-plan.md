# GamePause v0.3.0 — Implementation Plan

Version target: **0.3.0** (pre-release, matching the 0.2.0 release convention).
Branch: `v0.3.0` off `main`. Do **not** push or create the tag — Kynsi handles release and asks Ville for a final GO before anything touches `origin` or GitHub.

## 0. Hard constraints (do not violate)

These come from the owner and the app's core principles (lightweight, automatic, local support app).

1. **No new runtime dependencies.** The GUI stays native Win32 via `windows-sys` + Common Controls 6. Do **not** introduce egui, iced, Tauri, winit, Fltk, WebView2, wgpu, or any render stack. The only build-time dep allowed for assets is `winresource` (already present).
2. **No network, no telemetry.** Everything stays local.
3. **Code tests only.** Do NOT run interactive game tests and do NOT talk to a live LM Studio instance. Unit tests + the existing mock `LmStudio` backend (`src/lmstudio.rs::TestBackend`) are the test surface. The `#[ignore]` interactive tests stay ignored; do not add new live-protocol tests.
4. **Keep the thread model.** UI thread owns all windows; worker thread owns the `Engine`; the two meet only through the `mpsc` channel + the shared `Mutex` state. Do not move window handles to the worker.
5. **Preserve the reentrancy discipline.** Never hold a `RefCell` borrow (thread-local UI state) or the shared `Mutex` across a Win32 call that can pump messages (`TrackPopupMenu`, `GetOpenFileNameW`, `MessageBoxW`, `Shell_NotifyIconW`). The 0.1.1 tray crash was exactly this.
6. **Keep recovery semantics.** `state.json` is the source of truth. A relaunch after death must resume the pending restore. Never change journal format without a versioned read guard (the existing `deny_unknown_fields` + format-version pattern).
7. **Quality bar (already enforced by CI):** `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`. Match the existing style (no `unsafe`, explicit `#[must_use]`, small functions, doc comments on public items).
8. **Docs travel with code.** Update `docs/`, `README.md`, `CHANGELOG.md` as part of each item, not at the end.

## 1. Ground truth (verified before planning)

- Rust 1.98.1, `windows-sys 0.61` (features: Win32_Foundation, UI_Shells, UI_WindowsAndMessaging, UI_CtlWin32, Devices_HumanInterfaceDevice, Win32_System_Threading, Win32_System_SystemServices, Win32_System_Registry, Win32_System_Diagnostics_Debug, Win32_System_Pipes, Win32_System_LibraryLoader, Win32_System_Diagnostics_ToolHelp, Win32_Graphics_Gdi). **`Win32_Graphics_Dwm` is not yet enabled** — add it for dark-mode theming.
- `assets/GamePause.manifest` currently sets `<dpiAware>true</dpiAware>` (system-DPI-aware only). Per-Monitor v2 is not set.
- `assets/gamepause.ico` is **already** a multi-size icon (16/24/32/48/64/128/256 px, 32-bpp). **Icon work is already done — do not regenerate it.**
- `tray.rs` already sends an `NIF_INFO` toast (around `tray.rs:330-350`). Extend/standardize it; do not add a second toast mechanism.
- `dashboard.rs` hardcodes control backgrounds to `WHITE_BRUSH` / `SetBkColor(white)` in the `WM_CTLCOLORSTATIC` / `WM_CTLCOLORBTN` handler — this is why it looks like white boxes in Windows dark mode.
- `app.rs`: worker loop `App::run` (~`app.rs:385-440`); logging via `App::log` (`app.rs:553`); atomic `write_json` (`app.rs:607`); discovery worker thread (~`app.rs:369-377`); `Action` enum (`app.rs:27`).
- `engine.rs`: `Engine::new`, `Engine::restore`, `Engine::current_journal`, plus the capture/restore/verify primitives. Reuse these; do not reimplement the LM Studio protocol.
- CI: `ci.yml` = `test / fmt / clippy -D warnings` (ubuntu-latest). `release.yml` = on tag → Windows job → build + Inno Setup → upload `installer.exe`/`portable.zip` → `release-drafter` creates the pre-release from the tag.
- Release pattern (0.2.0): tag → CI produces artifacts → pre-release created from those artifacts.

### P0 — Crash resilience & correctness (the "degrade, don't die" layer)

#### P0-1. Transient filesystem errors must not kill the monitor
**What:** Stop the worker loop from exiting on a transient `inventory.json` write failure, a scan failure, or a momentary data-dir permission blip.
**Why:** Today `write_json(inventory.json)?`, `scanner.scan()?`, and `request_tx.send()?` in `App::run` propagate an error out of the main loop → process exits. If a pause was pending, the user is left with models unloaded and nothing watching. A support app must degrade.
**How:**
- In `App::run`, catch these per-tick errors, log them via `App::log` with a short consecutive-failure counter, and `continue` the loop.
- Introduce a bounded consecutive-failure counter. After **N=10** consecutive hard failures (or a non-recoverable condition such as the data dir becoming unreadable), transition the shared state to a new visible status (e.g. `status: "needs attention (data dir unavailable)"`) and keep the process alive so the tray can surface it. Do **not** `exit()` on transient errors.
- Keep `write_json` atomic (temp + `MoveFileExW`) — do not weaken it.
**Acceptance / test:**
- Unit test: inject a failing `write_json` (mock the writer or make the target dir read-only in a temp path) and assert the loop continues and the status flips to "needs attention" after N failures, not that the process ends.
- Test that a single failure does **not** change status (only N consecutive do).
- `clippy`/`fmt` clean.

#### P0-2. Discovery-worker panic must not kill the app
**What:** Wrap the discovery worker loop body so a panic in a third-party reader (Battle.net `product.db`, a 2 GB VDF, a weird registry tree) is contained.
**How:**
- In the discovery worker (`app.rs` ~`app.rs:369-377`), wrap each scan iteration in `std::panic::catch_unwind`. On panic: log the panic payload (stringified), keep the last good inventory, and continue with the next `tick`.
- Ensure `inventory_tx` still receives a valid (possibly unchanged) `GameInventory` after a panic so the UI doesn't stall.
**Acceptance / test:**
- Unit test: a discovery backend stub that `panic!()`s on one tick → assert the app keeps running and the inventory is unchanged (or stale-but-valid) on the next tick.
- No new live-protocol test.

#### P0-3. Global panic hook → log + clear message
**What:** Any panic on any thread should be written to the log and produce a stable, non-surprising outcome.
**How:**
- In `main.rs`, call `std::panic::set_hook` before starting the app: append the panic location + message to the log file (reuse `App::log`'s sink if reachable, else write to the data-dir log path directly), then run the default behavior.
- Ensure the log write itself never panics (best-effort).
**Acceptance / test:**
- Unit test: set the hook, `panic!()` in a thread, assert a line was appended to a temp log path.
- README: add a short "If GamePause disappears while a pause is pending, start it again — it resumes the restore" note (see P2-5).

#### P0-4. Contain a failed restore without dropping the journal
**What:** A failed `Engine::restore` must leave the pending journal intact and surface a clear "restore failed — AI not restored" state (partially present; make it explicit and tested).
**How:**
- In `App::run`, the `Err(e)` branch from `engine.restore()` currently logs + `continue`. Confirm it (a) does **not** delete/modify the journal, (b) sets the visible status to "restore failed — AI not restored, click Restore", and (c) the dashboard Restore button is re-enabled (gated on `active_mode && pending && discovery_ready`).
**Acceptance / test:**
- Unit test with the mock `LmStudio` backend: force a restore error, assert the journal file on disk is unchanged and the status string is the "restore failed" variant.

### P1 — UX + GUI polish (native, zero new deps)

#### P1-1. Per-Monitor v2 DPI (manifest only)
**What:** Crisp rendering on mixed-DPI multi-monitor setups.
**How:** Replace the `<dpiAware>true</dpiAware>` line in `assets/GamePause.manifest` with the v3 settings block (keep the existing `<assembly>` identity + `Common Controls 6.0.0.0` dependency):
```xml
<asmv3:application xmlns:asmv3="urn:schemas-microsoft-com:asm.v3">
  <asmv3:windowsSettings>
    <dpiAwareness xmlns="http://schemas.microsoft.com/SMI/2016/WindowsSettings">PerMonitorV2</dpiAwareness>
  </asmv3:windowsSettings>
</asmv3:application>
```
The `scale()` helpers in `dashboard.rs` already compute per-monitor sizes; verify the `WM_DPICHANGED` path resizes/relayouts (add if missing) so controls don't stretch.
**Acceptance / test:** Code test: the manifest parses (xunit) and the `scale()` math is unit-tested for 100%/150%/200%. (Live DPI verification is a manual smoke test on release — note it, don't automate.)

#### P1-2. Follow the system theme (the big one)
**What:** Stop the white-box look in Windows dark mode; make the window, controls, and title bar track the OS theme.
**How:**
- Enable DWM dark caption for both the tray-anchored window and the dashboard: add `Win32_Graphics_Dwm` to `windows-sys` features, call `DwmSetWindowAttribute(hwnd, 20 /* DWMWA_USE_IMMERSIVE_DARK_MODE */, &1u32, 4)`. Gate on the current system theme so light mode stays light (read `ColorsUseLightTheme` from `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize`, or simply always set dark when the app's own `dark` flag is on).
- In `dashboard.rs`, replace hardcoded `WHITE_BRUSH` / `SetBkColor(white)` in `WM_CTLCOLORSTATIC` / `WM_CTLCOLORBTN` with `GetSysColor(COLOR_WINDOW)` / `GetSysColor(COLOR_BTNFACE)` for backgrounds and `GetSysColor(COLOR_WINDOWTEXT)` for text. This makes controls theme-correct in both modes.
- Keep the existing `dark: bool` setting as an override; when unset, mirror the system.
**Acceptance / test:**
- Unit test: the `WM_CTLCOLOR*` handler returns a brush whose color equals `GetSysColor(COLOR_WINDOW)` (capture via the handler's return) rather than a literal `RGB(255,255,255)`.
- Manual smoke note for release: verify light + dark both look native.

#### P1-3. Group-box sectioning + tighter grid
**What:** Visual structure so the control field reads as sections, not a flat wall.
**How:** Add `BS_GROUPBOX` static controls around "Games", "Settings", and "Actions" in `dashboard.rs`; adjust the coordinate grid so controls align on a consistent column gutter and row pitch (derive from `scale()`). No new dependency.
**Acceptance / test:** Layout constants are unit-tested (group boxes present, controls inside their boxes' bounds). Manual smoke note.

#### P1-4. Owner-drawn listbox rows with status dots (Tier 2, optional sugar)
**Status: implemented 2026-10-04** — `LBS_OWNERDRAWFIXED` + `WM_MEASUREITEM`/`WM_DRAWITEM`; per-row dot color is the pure, unit-tested `dot_color(ignored, running)` (green=running, amber=pausing-off, gray=idle), DPI-scaled `row_height`, theme-correct bg/text via `GetSysColor`. See the P1-4 tests in `dashboard.rs`.
**What:** A small colored dot / "Running" indicator in the games list and a subtle state pill (paused / watching / restored) so the current engine state is visible without a tooltip.
**How:** Make the games listbox owner-drawn (`LBS_OWNERDRAW`) and handle `WM_DRAWITEM` in the dashboard proc: draw the item text via the existing font, plus a filled circle whose color maps to state (green=restored/healthy, amber=pending/needs attention, gray=idle). Use GDI (`CreateSolidBrush`, `Ellipse`, `DrawTextW`) — no new deps.
- Keep it optional: if it starts fighting the existing listbox logic, ship P1-2/P1-3 and record this as a follow-up.
**Acceptance / test:** `WM_DRAWITEM` handler unit test asserts the correct brush color per state; no crash on empty list.

#### P1-5. Pause & restore toasts + system sound
**What:** Confirm the two important moments. Right now pause is silent and restore is silent unless it fails.
**How:**
- Extend the existing `NIF_INFO` toast path in `tray.rs` (do not add a second mechanism) to fire on: (a) "Paused — N models captured", (b) "Restored — N models, config verified", (c) "Restore failed — AI not restored" (error toast, `MB_ICONHAND` equivalent).
- Play the system sound via `MessageBeep(MB_OK)` on success and `MessageBeep(MB_ICONASTERISK)` / `MB_ICONHAND` on failure. `MessageBeep` needs the `Win32_System_SystemServices` feature (already enabled) — add the constant import. No custom audio assets.
**Acceptance / test:**
- Unit test: the action→toast mapping table returns the right title/body/severity for pause-success, restore-success, restore-failed.
- Confirm `MessageBeep` is called on the mapped path (assert via a tiny indirection you can stub in tests).

#### P1-6. State-colored tray icon
**What:** State visible at a glance instead of a hover-only tooltip.
**How:** You already hand-draw the tray icon. Add two tinted variants (e.g. amber = pending/needs attention, blue = paused & watching) by drawing the same base glyph over a tinted background, and call `Shell_NotifyIconW(NIM_MODIFY)` when `active_mode`/`status` changes. Keep the base icon as the "healthy/idle" state. Reuse the existing icon-drawing code; no new deps, no new file (draw in memory with GDI).
**Acceptance / test:** Unit test: state → variant selector returns the expected variant for idle/paused/needs-attention.

#### P1-7. Fix the illogical usage paths
**What:** Remove the silent/confusing paths found in review.
**How (each is small):**
- **Tray "Restore AI now" pre-discovery** currently no-ops silently. Gate it on `discovery_ready` (mirror the dashboard) **and** when disabled, show a toast/tooltip "Restore unavailable until a game is detected" instead of nothing.
- **Pause/Resume manual toggle** label never reflects current state. Flip the button label (or add a checkmark) to "Resume AI" when manually paused; keep the tray checkmark.
- **Settings validation** currently pops a modal while discovery errors use the FEEDBACK line. Route validation errors to the FEEDBACK line; reserve modals for hard failures (e.g. data dir missing).
- **"Add game..."** names the game after the exe stem with no in-UI rename. Add a small rename affordance (or an editable name column) so you don't have to delete-and-re-add. If a full rename is too heavy, at minimum let the user edit the display name of a row.
- **`open_path` swallows `ShellExecuteW` failures** (`tray.rs:139`). Surface a toast on failure.
- **`dedup_by` after sort-by-label** (`dashboard.rs:184`) only removes adjacent duplicates; the same executable under two names can both survive. Dedupe on canonical path *after* sorting, or before — pick one and test it.
**Acceptance / test:**
- Unit test for each: restore-gated-on-discovery (assert disabled + feedback), label flip on manual pause, validation error routed to feedback not modal, dedup-by-canonical-path removes a two-name same-path pair, `open_path` failure path returns a visible error.

### P2 — Further development

#### P2-1. "Test round-trip" (highest value)
**What:** A dashboard button + `gamepause verify` CLI subcommand that runs the full pipeline **without a game**: capture configs → unload → verify server stopped → restore → re-read and field-compare. Reuses the existing engine primitives.
**How:**
- Add a `Action::Verify` (or reuse a command path) that drives the `Engine` capture/restore/verify primitives against the *current* LM Studio state, using the **mock backend in tests** and the real backend only when the user explicitly clicks it.
- Add a `Verify` CLI subcommand in `main.rs` (there is already a `--background` flag; add a small subcommand switch) that runs the same path and prints a human-readable result.
- In tests, exercise it with `TestBackend` — no live LM Studio.
**Acceptance / test:**
- Unit test with `TestBackend`: verify reports success when the mock round-trips, and reports the exact failing field when the mock returns a mutated config on restore.
- Dashboard button shows per-step results (capture/unload/stop/restore/verify) in the FEEDBACK area.
**Note:** This is the single most trust-building feature. Keep it self-contained.

#### P2-2. Doctor panel
**What:** A "Diagnostics" view (dashboard tab or a section) exposing: `lms` version, WS protocol check result, currently loaded models, server state, and data-dir writability.
**How:** Read from the existing `lmstudio.rs` state + `config.rs`; no new deps. Reuse the `--doctor`-style data if it exists, else add a small `diagnostics()` that assembles these from current structs.
**Acceptance / test:** Unit test: `diagnostics()` assembles the expected fields from a fixed set of inputs; assert the data-dir writability check returns false for a read-only temp path.

#### P2-3. CLI surface expansion
**What:** `status`, `games`, `verify` subcommands for scripting and the "is it even running?" moment.
**How:** Extend `main.rs` subcommand parsing (currently `--background` / `--data-dir`). `status` prints the current journal/state; `games` lists discovered games; `verify` is P2-1. Keep output plain text, stable, parseable.
**Acceptance / test:** Each subcommand unit-tested with the mock backend and a temp data dir; assert exact stdout shape.

#### P2-4. Per-capture/restore WS logging
**What:** Log LM Studio version + WS protocol success/failure and the field that failed, local-only.
**How:** In `lmstudio.rs`, on WS `loadModel`/`channelCreate`/config read, append the LM Studio version and a `success|failed:<field>` line to the log. Reuse `App::log`'s sink or a local logger.
**Acceptance / test:** Unit test with `TestBackend`: a failing field produces a log line naming that field.

#### P2-5. README "what if my PC dies mid-pause" section
**What:** A one-paragraph section explaining: journal persists → relaunch resumes restore. Pairs with P0-3.
**How:** Add to `README.md` under a new "Recovery" heading. Cite the actual behavior (verified in P0-4).
**Acceptance / test:** Manual review; no test.

#### P2-6. CI the interactive test (optional, Windows runner only)
**What:** `native_popup_survives_repeated_timer_reentry` currently lives as an ignored desktop test. If a Windows CI runner is available, run it as an opt-in job; otherwise keep it ignored and note it.
**How:** Add a gated job in `ci.yml` (e.g. on a Windows runner with a display server) that removes the `#[ignore]` for that one test via an env var, or a separate `test-interactive` job. Do **not** make it required on the default `ubuntu` path.
**Acceptance / test:** The default `ci.yml` still passes on ubuntu; the interactive job is additive and skippable.
**Note:** Low priority. If it complicates CI, drop to a roadmap note.
