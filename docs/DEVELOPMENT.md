# Development

## Build and checks

Windows x64, Rust 1.99.0 via rustup, Visual Studio C++ Build Tools, and the Windows SDK are required. The toolchain and dependency lockfile are committed.

```powershell
cargo test --locked
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo build --locked --release
.\target\release\GamePauseCLI.exe --observe --headless --duration 10 --data-dir .\scratch
```

`GamePauseCLI.exe` is the same program built as a console application. It is a development tool for tests, headless runs, `--doctor`, `--discover` and `--verify`; it is not packaged or documented for users. The shipped `GamePause.exe` accepts the same switches without console output, and reports `--restore` in a message box.

Default behavior automatically pauses AI. For non-mutating diagnostics, explicitly pass `--observe`. Use a private data directory for development. Do not overwrite a real pending journal, and do not commit runtime files.

During implementation, run tests relevant to the latest ticket. Run the full suite once for final candidate validation, then fix any failures. Formatting and Clippy remain applicable quality gates. Do not commit or publish unless the current task explicitly requests it.

P1-4 handles suspend and automatic resume. The tray routes [WM_POWERBROADCAST](https://learn.microsoft.com/en-us/windows/win32/power/wm-powerbroadcast); headless watchers use [PowerRegisterSuspendResumeNotification](https://learn.microsoft.com/en-us/windows/win32/api/powerbase/nf-powerbase-powerregistersuspendresumenotification), without another application thread. The later user-interaction resume event does not reset the delay again. Atomic generations invalidate in-flight scans and provider work at coordinator boundaries. The worker rebuilds process caches, rejects pre-event inventory generations, refreshes discovery and invalidates provider completion evidence before further control. Journal writes preserve original snapshots, completed restoration entries and Ollama deadlines/monotonic budgets. Failed writes hold control and honor retry backoff. Observation does not rewrite journals.

The characterized policy starts a full configured grace period after reliable post-resume discovery/process evidence confirms no games. Manual holds survive. Coexistence is held inactive while inventory refreshes, then revalidated against process identities; a failed/unknown scan revokes it. Only app restart revokes it unconditionally. Headless callback context uses an opaque registry ID, not an allocation pointer; deregistration removes the entry before native cancellation, preventing a late callback from accessing freed state. Successful headless shutdown checks native deregistration. CLI Restore/Verify also registers the callback and stops further units after a power change, retaining recovery for a later retry. Power API support is enabled in windows-sys; no dependency version or lockfile update is needed. Injected messages/callbacks do not prove actual sleep/wake delivery or live provider restart behavior.

The watcher polls native process metadata every two seconds by default on one persistent detection thread. Provider calls stay on the existing control thread, so a blocked capture/load does not stop periodic detection. The scanner only queries executable paths for new `(PID, creation time)` pairs, matches each known process against the inventory once per scan, and compares paths in place (`discovery::inside`/`same_path`) without allocating. Settings are compared by value, not by serializing them. A failed search for the LM Studio CLI stands for 30 seconds before `PATH` is walked again. Inventory refresh runs on a separate worker and retains the previous successful adapter inventory after errors. No installed-game directory tree is recursively scanned. Xbox folder roots are looked for on fixed drives only (`GetDriveTypeW`), when forced and otherwise every five minutes, and cached between; package discovery uses a bounded PowerShell query on the same cadence and is deferred during gaming.

Detection has one replaceable input and one latest result, with no per-tick thread or queued scan backlog. Settings/inventory changes invalidate scans begun against older input. Automatic control, manual Restore, gameplay confirmation/retry and round-trip verification request a scan begun after each guard request; a two-second timeout, scan error or stopped scanner is unknown detection and holds control. The timeout bounds the guard wait, not native enumeration itself. A scanner panic wakes waiters and marks detection unavailable; it does not spawn a replacement thread.

The scanner publishes detection/game rows to shared native status while control is busy. It takes no engine ownership or provider action, and no mailbox/UI mutex spans process enumeration. Engine grace, retries and gameplay authority stay on the control thread. Normal ticking cannot overwrite newer scanner-owned rows with an older frame. Fresh guards still interrupt only between provider units; a model load already in progress must return before remaining loads can be deferred. CLI `status.json` remains the last control-tick report, and inventory acceptance still waits for the control loop. Unknown/unregistered games and OS process-query stalls remain detection limits.

The tray uses Win32 directly. The dashboard, introduced in v1.5.0 and restyled in v1.6.0, uses eframe/egui with Glow and AccessKit; there is no webview or frontend. Completed gaming pauses do not repeatedly contact LM Studio or rewrite the journal. Runtime status is written only when it changes, with bounded log rotation. The dashboard starts on demand on one dedicated UI thread. Closing releases the window and renderer; the UI thread waits on its mailbox and reuses its event loop when reopened. It exits on watcher shutdown. Running-app rows are produced only while the Running apps page is visible. Settings travel through the worker action channel, validate and save atomically before replacing scanner/backend configuration. Turning off automatic pausing still allows recovery after recognized games exit. The old broad Steam-library fallback is replaced by a one-shot refresh request for new unfamiliar processes inside known libraries.

## LM Studio integration

The engine drives pause/restore through the common provider router, coordinator and LM operation units, which call `provider::Backend`. Associated payloads remain adapter-owned: the contract does not require LM JSON, namespaces, ports or raw fields from another provider. The router rejects mismatched kind/payload pairs and refuses execution when a queued unit's exact binding has changed. LM owns schema-2 payload validation, legacy normalization, original service-state decisions and optional raw-field read-back comparison. The engine owns gameplay policy; the coordinator checkpoints durable intent and retains failed obligations. Production storage and routing retain typed LM and Ollama obligations. Ollama is a regular provider, enabled by default, with live evidence for Ollama 0.35.1 and 0.40.0 only. Malformed or duplicate loaded identifiers produce unknown residency, never proof of absence. Settings are version 4 and the recovery envelope is version 3; the embedded LM snapshot retains its schema-2 representation.

Between control ticks the engine retains process-local coordinator state: independent provider deadlines, completed work, model-local failures, verification progress and failed persistence. This continuation is not serialized authority. Restart reconciles the durable journal with fresh adapter evidence. Automatic work uses each provider's deadline; explicit manual requests permit an immediate retry. Healthy completed providers are not queried again while another provider retries. Failed writes or journal clears retain a global persistence gate and the engine's storage backoff. Independent remembered-game saves invalidate continuation and require reconciliation. Whole verified restoration discards it before another session starts.

Provider reports reach shared dashboard/tray status at unit boundaries and appear in CLI `status.json` as `provider_outcomes`; the CLI line protocol is unchanged. Basic summaries show each enabled provider's operation result, pending recovery and failure without Advanced settings. Disabled providers stay hidden. The dashboard hero shortens these to one phrase per provider; tray text and `status.json` keep the detailed wording. Restoration is labelled as completed past work (**Models restored**), and idle text (**Ready**) never states current residency, which stays unpolled. Retry seconds describe the last report rather than a live countdown. Native error excerpts flatten whitespace and cap at 300 characters; worker detail and JSON retain the full error.

Settings contain one entry per provider kind with a stable ID and validated loopback host/port. `localhost` and `127.0.0.1`, including equivalent decimal port spellings, share one normalized endpoint identity. Duplicate IDs/kinds/endpoints and unknown fields/versions are refused. LM owns its nested connection settings; Ollama has only its endpoint and identity and is enabled by default. Settings are version 4. `Config::decode` chains migrations: version-2/unversioned input is first shaped as version 3, and version 3 becomes version 4 by enabling the Ollama entry once (unless the file carries the interim `ollama_default_applied` marker, which records an owner's choice and is dropped). `Config::load` keeps the source bytes as `config.v2.backup.json` or `config.v3.backup.json` under the same conflict rules before its atomic replacement; `Config::parse` migrates in memory only. Unit tests build default settings with Ollama off so they never reach a developer's service. An empty/all-disabled provider set does not start control; pending schema-2 recovery requires LM to stay enabled and configured. Live settings edits cannot disable/remove its entry or change its ID/endpoint during recovery. Recovery still uses the original journal port, including nondefault ports.

`Config::load` validates and atomically migrates version-2 or unversioned files, keeping the original bytes in `config.v2.backup.json`. A different existing backup, failed backup, invalid source or failed atomic replacement stops migration and retains the source. The matching backup supports retry after a failed replacement. Version-2 observation mode and explicit automation choices survive; unversioned files keep the previous one-time active-mode migration rule. `Config::parse` performs the same conversion only in memory for Doctor. Backups are never read as active settings. See Usage for downgrade instructions. Advanced visibility defaults off; notification and sound preferences default on. Advanced visibility and notification controls/delivery are integrated; human delivery acceptance remains UX-6.

The CLI supplies model/server inventories and unload/start/stop operations. Native `/api/v1/models` supplies additional settings. The internal `/llm` and `/embedding` WebSocket interfaces supply raw load configuration and load models using an API override layer. Capture can temporarily start the server when it was initially stopped, and always attempts to stop that temporary server even if capture fails. Recovery uses the recorded server port and original running state. This preserves settings outside the public SDK's simplified configuration surface.

The protocol is an internal dependency, not a stability promise. Relevant primary references: [LM Studio CLI](https://lmstudio.ai/docs/cli), [native REST API](https://lmstudio.ai/docs/developer/rest), [LM Studio Python SDK source](https://github.com/lmstudio-ai/lmstudio-python), and [Windows Toolhelp process snapshots](https://learn.microsoft.com/en-us/windows/win32/toolhelp/taking-a-snapshot-and-viewing-processes). Check protocol changes against the official SDK source and run a full live cycle before shipping.

`ollama_contract.rs` supplies the production adapter and isolated evidence fixtures. Bounded inventory parsing rejects ambiguous identity/digest/routes and unknown locality. The replay subset is local GGUF models advertising `completion` (any additional capability except `embedding`) with explicit local routing, supported observed context and parseable expiry. Other verified-local residents become unload-only entries; remote or changed content refuses capture. Acknowledgement is distinct from verified absence/final residency. Source research targets Ollama v0.35.1 at commit b0c1ca4f7549d7acdfa52a7dcffc934bc63a43ce, and the live checks in [the Ollama review](v1.0.0-ollama-review.md#live-evidence) used that version and, for the 2.1.0 check, 0.40.0. See [the supported subset](USAGE.md#background-ai-applications).

`ollama_expiry.rs` implements two persisted policies, selected by the snapshot's `expiry_policy` string. New captures use `frozen-remaining-v1`: the residency remaining at capture is replayed whole, no clock is consulted, there is no capture limit, and a remaining time of a century or more (Ollama reports `keep_alive: -1` as roughly 292 years) is replayed as `keep_alive: -1`. Journals written under `absolute-observed-deadline-v1` keep that policy: finite deadlines within a 24-hour capture limit, paused time consumed, a monotonic in-process budget and replay refused when a post-restart clock precedes capture. Unknown policy names are refused and the journal retained. Calendar/offset/precision, malformed data, expiry, clock-limit and frozen/indefinite fixtures cover both.

CLI inventories may report a base `modelKey` plus `selectedVariant` before loading, then a variant `modelKey` after loading by variant. Identity validation accepts equivalent representations while refusing a different quantization/file. The loader checks the saved variant remains selected and uses the catalog base key so instances remain visible through native REST. Raw key/value fields are compared independent of ordering; native exposed fields are also checked. Changed variant selection retains recovery and requires resolving the catalog selection.

## Recovery rules

The engine retains the complete journal as authority; its public LM snapshot is a compatibility projection. Pending detection, gameplay guards, verification refusal, command completion and shared status use all obligations. Single-LM extraction returns an error for mixed/Ollama journals. Remembered-game saves keep every original provider payload and completion marker. Mixed partial restoration can mark LM verified without clearing Ollama or claiming whole-session completion; retrying unavailable Ollama does not query completed LM work again. Disabled/missing experimental enrollment remains a retained, provider-qualified failure while healthy LM restoration proceeds. Active LM-only binding refusal and schema-2 migrations retain their previous checks.

Pending provider edit guards validate the affected unresolved binding; unchanged presentation preferences can save even when experimental enrollment is unavailable. Persisted verified obligations remain complete across restoration retries/restart, even if their provider is disabled, removed or reassigned. A new pause atomically retires such completed entries when their original provider is no longer enabled at its bound route, before further control. Unfinished originals remain untouched. A failed retirement write holds all control and keeps the authoritative journal. An unchanged enabled provider instead reuses its original capture for repause.

A session with every restoration already verified can clear with every provider disabled, without provider calls. When retirement clears the last verified entry before a new capture, the engine clears its compatibility projection too; a refused fresh capture cannot resurrect the old recovery. These checks do not permit clearing an unfinished disabled provider's obligation.

`ollama_session.rs` implements the adapter. It captures matching catalog/resident identity, then rereads residency before accepting capture. Replayable models record context and deadline evidence; other local residents are recorded in the optional `unload_only` list with identity and unload stage only. Its typed snapshot records the pinned source revision, expiry policy, immutable original candidates, acknowledgement stages and expiry resolution. It refuses changed versions/policies, inconsistent deadline evidence, duplicate names and replacement of originals. The `unload_only` field is omitted when empty, so earlier journals still load; builds without it refuse and retain a journal that has it. `Runtime::note` reports unload-only names through `Report.note`, which the coordinator keeps on the provider status after the journal clears. The type is part of `recovery::Payload`; the bounded executable loader accepts one or both supported provider entries and retains every obligation. Advanced offers a plain enable checkbox and endpoint field in the shared settings draft; there is no opt-in dialog.

LM Studio has the matching rule at engine level. `lmstudio::Backend::installed` reports whether the CLI can be found; when it cannot and no LM recovery is owed, `Engine::control_config` leaves LM Studio out of control exactly as if it were disabled, and `lm_missing` reaches shared state. The dashboard's status card (`dashboard::listed`) names only apps the PC has: LM Studio unless `lm_missing`, Ollama when `Shared::ollama_installed` (its program file in the per-user install folder or on `PATH`, looked up with each inventory refresh), when its process is running, or when a report from the current session holds work. The detection frame carries `lm_running`/`ollama_running` from the process cache it already has, so an idle listed app reads **Not running** or **Ready** without contacting the service. The same applies to a closed LM Studio: the watcher sets `Engine::lm_closed` from the scanner's process evidence (`LM Studio.exe` or `llmster.exe`) before each step, and while nothing is owed to LM Studio (`lm_idle`) it is left out of control and of the round-trip test. Every `lms` command starts LM Studio when it is not running, so a game must not reach the CLI for an app that is closed; once recovery is owed, starting it is intended. `run_command` treats a command as finished 250 ms after it has exited with quiet pipes, because the LM Studio process `lms` starts inherits those pipes and never closes them. `Engine::nothing_held` recognises a session whose journal holds no model and no stopped server: it changes the status wording and skips the pause/restore completion counters that drive success notifications.

Unknown-game suggestions are computed on the detection thread and never reach the engine. `processes::fullscreen_foreground` reads the foreground window's rectangle, style and owning process (geometry queries only, no message to that window, and the handle is not kept); `Scanner::suggestion` rejects known games, helpers, exclusions, Windows components and a list of common fullscreen programs. The scanner frame publishes a path only after it has led five consecutive scans and is not in `dismissed_suggestions` or `ignored_games`. The tray shows it through the same once-per-appearance prompt as ask games; the dashboard offers the existing Add dialog or a dismissal saved through the normal settings action. No GPU counters are read, and the heuristic was not exercised against a real fullscreen game.

The process provider (`Kind::Process`, `Payload::Process`) stops configured executables and relaunches them. `Providers` handles it directly beside the two-way LM/Ollama `Router`, through an engine-owned `ProcessRuntime`. Its binding uses the fixed route `local-processes` instead of a port; binding validation special-cases it, and it takes no ownership claim. A process that owns no top-level window (a console server) is terminated without the three-second close wait. The adapter captures one entry per top-level instance (a process whose parent runs from the same file is part of its parent's instance), stops by path behind a `Stopping` checkpoint, verifies that nothing at a captured path remains, and on restore starts the n-th instance only while fewer than n are running, so a lost response or a manual restart is not duplicated. A retry re-plans each stop or start behind its own checkpoint. Start details come from the target's 64-bit process parameters (`NtQueryInformationProcess` plus `ReadProcessMemory`); a failure there fails capture before anything is stopped. `seal`/`open` use `CryptProtectData` with UI forbidden, hex-encoded; nothing else of the command line is persisted or logged, and diagnostics list names only. The journal accepts up to three provider entries. Round-trip verification does not include it. No real llama.cpp or KoboldCpp was run.

`pause_hotkey` is parsed by `config::parse_hotkey` and validated with the settings. The tray's hidden window owns the registration: its status timer compares the saved text with the last applied text and re-registers with `RegisterHotKey` (`MOD_NOREPEAT`) on the tray UI thread with no lock or borrow held; `WM_HOTKEY` routes through `request_core`/`restore_dialog::request`, the same paths as the tray menu. Headless runs register nothing.

The `ask_games` rule is applied in detection: the scanner frame and `evidence_from` leave unanswered ask games out of the triggers, and the frame lists running ask games in `asking`. The watcher loop owns the answer (`Action::PauseForGame` sets it; it resets when no ask game is running) and publishes unanswered names as `Shared::ask_prompt`. Guard scans for restore treat ask games as non-triggers. The notification queue delivers one `Kind::Ask` event per appearance.

The memory-freed figure is presentation only and never persisted. `LMStudio::snapshot` sums `sizeBytes` from its capture inventory and the Ollama adapter sums `size_vram` (falling back to `size`) from its capture read; `Engine::captured_bytes` adds them for providers whose journal entry holds models, once per fresh pause, and clears the figure when recovery clears.

Round-trip verification runs the LM phase when LM Studio is enabled and installed, then `verify_ollama` when Ollama is enabled. `verify_scope` restricts the pause and restore drivers to the provider under test, so each phase has its own journal session.

A connection refused on the first capture read is typed as `Unreachable` and produces an `absent` snapshot with no models: Ollama is not installed or not running. Such a session sends Ollama no further request, completes pause and restore from the journal alone, and reports `NOT_RUNNING` through the provider note, which the dashboard shows as **Not running**. Timeouts, HTTP errors and a service lost after models were captured remain failures with retained recovery.

The common router dispatches both actual adapters. Engine ownership retains the Ollama adapter's monotonic clock and non-waiting endpoint claim between control ticks, retries and coordinator validation failures. Capture claims the route before HTTP reads; mutations recheck ownership before generate. No ownership mutex spans network work. Each new capture starts its own time budget. Disabled or observation configuration refuses Ollama control while retaining an existing adapter and claim; settings replacement releases a provider's claims only when it has no unfinished recovery obligation. Private HTTP engine fixtures use explicitly enabled validated settings and cover mixed sessions, independent healthy LM completion, disabled Ollama/re-enablement, disabling completed LM followed by Ollama repause, and Ollama-only restart.

The HTTP implementation accepts only normalized loopback routes, disables environment proxies and redirects, requires HTTP 200 and caps every response at 1 MiB plus one overflow byte. Requests time out after ten seconds, except a generate request that keeps the model resident: that is a load, which answers only once the model is resident and which Ollama abandons when the client disconnects, so it is allowed 300 seconds like an LM Studio load. Unloads (`keep_alive: 0`) keep the short limit. It exposes only resident/catalog reads, show and generate. Adapter mutations revalidate catalog/show, use empty prompts and explicit local routes, and run after persisted intent through coordinator units. Capture is bounded by the 256-model evidence limit, but may issue many sequential requests; that limit does not imply a short capture latency. It never starts/stops the user-owned service, downloads models or sends inference.

Unload acknowledgement does not prove absence. Final inventory checks every captured digest, replayable or unload-only, under any alias and refuses other remaining content; continued residency defers with backoff. A successful pause remains quiet, so the adapter does not fight later external reload. Restore loads serially and verifies the whole final identity/context/residency set of the replayable models; unload-only entries carry no restore obligation. Eviction retains recovery and allows a bounded retry. Under the frozen policy a replayed residency shorter than the remaining restore work can end before final verification; the adapter recognises that from its process-local load times and resolves the model as expired instead of reloading it. Under the legacy absolute policy, expired obligations remain expired after restart, and a load that outlives its budget keeps an expiry-pending stage until read-only content absence, without further load/unload requests.

Eighteen adapter fixtures include private HTTP lifecycle and redirect/oversize refusal, delayed unload, pre/post-effect failures, typed restart, legacy expiry and over-budget loads, eviction, changed catalog, between-load game interruption, frozen replay after a long pause and across restart, indefinite residency, unload-only models and short frozen residency. They do not run vendor code. Live checks against Ollama 0.35.1 and 0.40.0 are recorded in [the Ollama review](v1.0.0-ollama-review.md#live-evidence); physical UI acceptance and other Ollama versions remain unproven. The limited guarantee excludes original load options/parallelism, conversation/KV state and exact vendor expiration timing.

`recovery.rs` reads at most 16 MiB plus one overflow-detection byte and bounds serialized writes to the same limit. Schema 3 contains shared remembered games and pause/restore/reconcile intent, stable provider bindings and versioned typed payloads. The LM payload keeps all original raw settings, model stages and server intent. The captured actual server port can differ from the configured port; the envelope records both and rejects reassignment of the configured identity/route. It rejects unknown fields/payload versions, inconsistent routes/games and unsupported provider sets rather than discard recovery. The current executable accepts one entry per supported provider kind. Ollama user enrollment is explicit and experimental; no live compatibility is claimed.

Active startup validates schema 2 before creating and flushing a byte-identical `state.v2.backup.json`, then uses the existing atomic replacement. A matching backup permits retry after a failed replacement; a different backup refuses migration. Observation and Doctor do no migration writes. Backups never become active authority. Clear the journal only after verified model/service completion and a successful atomic write. Transient gameplay authorization is absent from the journal and starts empty after restart. Follow the Usage downgrade instructions; older builds cannot recover schema 3.

Notification policy consumes coherent typed activity/completion evidence on the existing two-second tray timer. It queues at most one success, initially waits two seconds after observation, replaces pause with rapid restoration and drops invalid or excessively old success. The current lag bound is ten seconds after the due time; neither value is a fullscreen-delivery promise. `tray::failure_due` decides what counts as a failure: `PartialFailure`, `Recovery` (except the post-resume grace message) and any "Needs attention" message at once, and `DetectionUnavailable` only after ten consecutive timer ticks, so a wake from sleep or a start-up scan is silent. Failure notices have retry/countdown changes coalesced until a confirmed healthy state. Partial/recovery state cannot emit restore success. Success messages describe verified saved AI without claiming full Ollama settings preservation; Basic provider rows carry independent outcomes.

The sink chooses exactly one visual or sound-only path. Visuals use `Shell_NotifyIconW` with `NIIF_NOSOUND` when silent and `NIIF_RESPECT_QUIET_TIME`; `NIF_REALTIME` discards a notification Windows cannot display immediately. Only sound-only mode calls `MessageBeep`. A failed API call is logged once with no sound fallback or retry; API acceptance does not prove the user saw the message. See [Microsoft's notification flags](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-notifyicondataw). No state borrow or shared lock spans delivery. Preferences save independently through the worker, with stale hidden dispatch refused and no optimistic shared config. No new idle thread, provider polling, game overlay or focus stealing is introduced for delivery.

Advanced visibility is applied only after a validated settings save and follows shared config on refresh/reopen. Hiding the section moves focus to its checkbox and native dialog navigation skips hidden children. Dashboard/tray use shared command IDs and verification availability. The menu orders core commands before advanced tools and labels Quit exactly. Startup/folder helpers revalidate current visibility after nested menu dispatch; advanced settings and verification revalidate again on the worker. CLI verification retains its independent engine guards and does not require the presentation preference. A rejected stale Verify clears transient busy state. Future diagnostics tools must use this same visibility rule.

1. Capture every loaded instance and complete available settings before unloading.
2. Write intent atomically and flush before stopping the server, unloading, or loading.
3. Preserve the original snapshot across partial errors. Retry with backoff.
4. Recheck game processes before starting recovery and between model loads. A new game interrupts restoration; the next tick returns to pause.
5. Clear recovery only after all captured instances and the original server state are verified.

Observation mode does not execute pending recovery. Unknown journal formats are rejected. The exclusive Windows file handle prevents concurrent mutation through one data directory. Grace and retry timing use monotonic elapsed time.

LM control also obtains machine-global named-object claims before capture or mutation. Normalized endpoint keys are independent of provider ID/data directory; configured and actual capture/recovery routes are both claimed. LM adds a service claim because its CLI does not select the service by the configured API port. Existing named objects and access errors refuse control without waiting. Read-only inventories/Doctor and observation take no claim. The handles live in shared worker-owned state through transport replacement and pending-recovery preference saves. A provider settings change after recovery completes releases the obsolete set; process termination closes the handles. This guards cooperating new GamePause instances, not third-party clients or older builds. The existing journal/data-directory lock remains required.

The implementation uses named-object existence with an unowned mutex handle, never a thread-owned mutex wait. Claim-set replacement acquires all new routes before dropping obsolete ones; failures roll back new handles and retain the previous set. Isolated process fixtures verify contention and termination cleanup using private object names. See Microsoft's [CreateMutexW contract](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexw) for atomic creation/existing-object reporting, default access permissions and last-handle lifetime. No UI lock or borrow spans provider work.

`coordinator.rs` adds a compiled scheduling core with two distinct fake payloads. Each call captures one provider or executes one serial unit, with independent provider retry deadlines and statuses. Adapter validation checks transitions preserve original capture data. Each unit checkpoints intent before control and persists its result; failed storage holds all control and retains dirty state for retry. Captured/healthy work survives another provider's failure. Missing providers retain obligations. Restart resets completion evidence and reconciles from the saved stages. A fresh caller-supplied guard runs before work, after checkpointing, after work and before clearing. Game/grace/manual/coexistence policy remains engine-owned, and no gameplay authorization is serialized.

Recovery `Entry` and `Journal` now have generic payload types with the existing production payload as the default. Their existing serialized shape stays unchanged when the optional per-entry `restore_complete` marker is false/absent. The marker is persisted only after final promised-field and original lifecycle verification; all entries must finish before clearing. Prior supported schema-3 envelopes remain readable. Older intermediate builds that reject this new field retain those journals rather than drop it. The production `JournalFile` store uses existing bounded/atomic recovery persistence; unsupported real provider payloads/sets are still refused.

The engine's LM pause path now drives the coordinator and `LMRuntime` units. The adapter checks original route, loaded identifiers, busy evidence and actual server state, then checkpoints before each stop/unload and verifies their effects. Completed pause keeps the quiet fast path; restart recovery goes through reconciliation before a new pause completion. The synchronous pause driver bounds its unit count by captured model count plus four and retains recovery if work does not converge. A failed write cannot leave an in-memory completed-pause claim.

Each unit selects/claims the captured control port without starting a service. This keeps both configured and actual route claims when the optional transport is recreated. A known newly loaded model outside the original capture prevents completed pause; it remains untouched and the original snapshot is retained. Completed pauses still do not poll for later external changes.

The same LM adapter has restore units for ensuring the original port, one model load, one read-only model verification and final residency/original service verification. A successful server command is insufficient evidence of the final state. Read-only verification refuses a missing model without loading it. Adapter transitions preserve original model identities, namespace, TTL, raw/native settings and server JSON; only stages, intent/completion and remembered games change. New backend verification methods default to refusal, not acknowledgement-based success.

The engine's restore path now drives these coordinator units. A model load or read-only verification failure leaves that model pending while other LM models continue. Provider status retains the error and retry deadline through healthy progress; the failed model cannot retry early or authorize completion. Global planning, route and persistence errors hold control. A retry or restart resets transient failed-model and verification evidence. Partial recovery never closes the original service or clears the journal. Empty legacy recovery also requires proof of the original service state; unexpected external startup is retained without stopping it when no saved control intent exists.

The synchronous restore driver bounds work by twice the captured model count plus six. Fresh game guards run before/after units and before clearing, and engine progress is synchronized even after failed writes. Production multi-provider routing and native partial summaries are integrated. One unit per call bounds operation count, not elapsed time. Synchronous capture/model loads can still take a long time, but independent scanner scheduling now continues through blocked control. Tests with a 20 ms fixture period measured six native Toolhelp scans with maximum gaps of about 32–41 ms while mock control was held. Production keeps the configured poll period; these local results are not a live provider or hard OS latency guarantee. Full idle/performance acceptance remains P1-5.

Recovery waits for the first discovery result. The journal also remembers games seen during its session; removing or ignoring an entry cannot make an already-running game disappear from recovery checks. Old journals without these paths remain readable. Manual restoration uses the same discovery gate and checks recognized games even when user exclusions disable new pausing.

## Packaging

Install Inno Setup 6 (tested with 6.7.3). Run:

```powershell
.\scripts\build_release.ps1 -Iscc 'C:\Program Files (x86)\Inno Setup 6\ISCC.exe'
```

This builds both native executables, copies docs and dependency licenses, packages a portable ZIP, compiles the per-user installer, and writes `dist\SHA256SUMS.txt`. Release optimizations use size optimization, LTO, stripping, and one codegen unit. The Windows target config statically links the C runtime, avoiding a separate Visual C++ redistributable. Destination PCs need no language runtime. See the [Rust linkage reference](https://doc.rust-lang.org/reference/linkage.html#static-and-dynamic-c-runtimes).

CI runs formatting, tests, Clippy and the release resilience probe on every branch push and pull request; tags are left to the release workflow. The installer's final page starts GamePause with `--background`, so setup ends in the tray without a dashboard window; Start menu and desktop shortcuts open the dashboard.

## Releasing

1. Set the version in `Cargo.toml`, `Cargo.lock` and `installer/GamePause.iss`.
2. Add a `## <version> — <date>` section to `CHANGELOG.md`. It becomes the release notes verbatim, so write it for users and include anything known to be untested that they should hear about.
3. Run the quality gates, commit and push to `main`, and wait for CI.
4. Tag the commit `v<version>` and push the tag.
5. After the release is published, set `version` and the ZIP `hash` (from the release's `SHA256SUMS.txt`) in `bucket/gamepause.json`, the Scoop manifest, and push.

The release workflow then runs the tests, builds the installer and portable ZIP, runs `scripts/verify_release.ps1` (checksums, version metadata, default preferences, dependency license texts, no internal or runtime files in the archive) and publishes the GitHub release with the installer, ZIP, `SHA256SUMS.txt` and `BUILD-INFO.json`. It refuses a tag that does not match the package version or a version with no changelog section. Nothing is uploaded by hand. A manual run of the workflow builds the same packages as a workflow artifact without publishing. Binaries are unsigned. Release only when asked to.

## v1.0.0 candidate implementation (historical native dashboard)

The engine publishes capture/unload/restore progress to shared state before bounded synchronous provider work. The observer takes only a short shared-state lock and makes no Win32 calls. Dashboard and tray consume the same `ControlState` availability policy. Worker dispatch revalidates engine state, detection readiness and a fresh exclusion-free game scan; restoration still checks remembered games between loads. Pause and Resume are explicit commands, so repeated Pause cannot toggle a hold. Discovery errors hold automatic control/recovery and manual commands until a successful inventory and process scan establish detection readiness.

Completed pause requires a final captured-instance absence check and a successful journal write. A failed final write leaves pause incomplete for retry. Once completed, pause ticks retain the existing quiet behavior. Published progress is transient; durable intent and adapter stages live in schema-3 recovery. CLI field formatting remains compatible. Provider routing and dashboard theme drawing are integrated; physical/human acceptance remains pending.

User commands carry transient request IDs and typed outcomes separately from engine state and historical verification. Only the latest user request can replace its feedback; timer ticks cannot restore an older result. Manual Pause/Restore completion follows engine evidence. Gameplay restoration preserves its independent Ignore-save result. Refresh requests coalesce and bind to a future discovery dispatch generation, so accepting an older in-flight result cannot claim completion. Adapter errors report failed refresh with last-good entries retained; worker/channel failures terminate pending refresh feedback.

Settings requests keep shared config unchanged until validated atomic persistence succeeds. Concurrent preference requests are refused while a save is pending, including gameplay Ignore saves. Remove selected sends the custom path and name to the worker, which validates them against current settings and removes only that entry. Save failure preserves config, rows and remembered recovery paths. The native confirmation defaults to Cancel. Row selection follows canonical paths across unrelated updates. Picker cancellation/errors and folder/startup outcomes use the same command feedback; no new result fields are persisted or added to CLI output.

Gameplay Restore uses a one-use offer containing PID, creation time and executable path for each recognized process. The worker rechecks the exact set after confirmation and before/between loads. Approval lives only in memory. A new nonignored trigger, an approved process exiting/relaunching, unknown evidence, manual Pause or restart revokes it. Approved game registrations remain in scans even if removed from settings. Ordinary Restore and Verify never receive this exemption. Partial loads keep the original journal; retries remain subject to fresh process evidence.

Ignore selections save only selected canonical executable exclusions, independently of restoration. The native dialog releases shared locks before its nested message loop, prevents reentry, defaults to Cancel and does not post a thread quit message when closed. Internal process identity fields are excluded from cached status JSON. Failed enumeration or inaccessible previously recognized/explicitly registered game processes make evidence unknown; unfamiliar protected processes remain subject to the existing recognition limits. No scan-performance claim follows from the fixture tests.

## v1.5.0 dashboard development

[The implementation journal](history/UI_V1.5.0_JOURNAL.md) records the current redesign and acceptance status. `dashboard.rs` consumes cloned shared state and sends existing tracked worker actions. It never creates provider adapters or performs model operations. The UI bridge sends egui contexts and typed requests between the tray and dashboard UI threads; no HWND crosses to engine workers. Shared/bridge locks are released before renderer or native modal dispatch. The dashboard reads tray requests while drawing a frame, and a minimized window draws none, so `dashboard::dispatch` first restores a minimized window with `ShowWindowAsync` from the tray UI thread (the handle is kept in the bridge for that purpose only, with no lock held across the call); `close` waits at most three seconds for the renderer thread. Tray timers compare state before requesting repaint, copy only the fields they need under one short lock, and call `Shell_NotifyIconW` only when the icon state or tooltip changed. Closed dashboards have no window or renderer and do not poll/redraw; five-second toast expiry requests one scheduled repaint. Activity holds at most 160 observed changes in memory, with unchanged frames adding nothing.

Advanced edits use one config draft and existing validated atomic worker saves. When the shared revision changes under a dirty draft (an instant preference, a game rule, an inventory refresh), `rebase_draft` merges field by field: values the draft left alone follow the saved settings and edited values stay; an invalid merge falls back to the saved settings with a message. Escape with a dirty draft opens a discard prompt. Provider recovery gates and exact experimental-enrollment confirmation remain in place. Gameplay confirmation keeps the offer ID and initially unchecked executable exclusions; the worker performs fresh process checks before accepting it. The old Win32 dashboard geometry/GDI tests were replaced because those controls no longer exist; pure save, rename, registration and verification-report regressions remain.

`presentation::status()` folds every `control::Activity` into one of four `Look` values (Running/blue, Paused/orange, Loading/yellow, Attention/red) with a short title and hint; a unit test pins the full mapping. The dashboard's `hero()` adds its glyph, and the tray menu header shows the same state in two rows. The look selects the palette, the window icon and the hero glyph, and the palette is reinstalled only when appearance, contrast or look changes. Unfinished recovery and failures use Attention, never the Paused title. The primary button is inert and reads **Loading...** only while a Loading activity leaves no command available; otherwise shared `ControlState` availability decides, as before. The native caption is tinted through `DwmSetWindowAttribute` on the dashboard's own UI thread with no lock held; Windows 10 ignores the color attributes, and high contrast restores the system caption. Buttons and tabs are painted but allocate ordinary egui responses, so focus, Enter/Space activation and AccessKit roles are unchanged.

`game_icons.rs` supplies executable icons for visible rows and the selected entry. Requests go to one `gamepause-icons` thread that exists only while a dashboard window is open and exits when its channel closes. It never runs on the watcher, detection or control threads and takes no shared lock. For a folder it lists that folder and at most two levels below it, capped at 2,000 entries and 48 folders per level, without following links, and picks the largest executable at the shallowest level that has one, skipping common installer/crash-handler names. A running game's known executable is used directly. `PrivateExtractIconsW` output is converted on the loader thread; textures are created on the UI thread, and the cache holds at most 512 entries. This lookup is for presentation only: detection still performs no recursive installation scan. Missing, protected or over-long paths fall back to the generic glyph.

Table columns sort in memory on the UI thread; the Status column was removed because the hero and Running apps already name running games. Refresh moved to Advanced > Detection.

The tray menu is a fixed set of quick controls: two state rows, the automatic-pausing toggle, Pause AI, Resume AI, Open GamePause and Quit. It does not grow with the Advanced preference and carries no provider details, command feedback, Refresh or diagnostic tools; those are dashboard-only. A unit test pins the order and requires each tray command to have a dashboard counterpart that needs no Advanced toggle.

Focused UI tests render all typed activity states and pages at compact, normal and large sizes, with 100/125/150/175/200% scale factors. The single ignored `ui_design_review_snapshots` fixture renders fictional state, including all four looks and stand-in icon tiles, in its own eframe window and exports that window's framebuffer to `scratch/ui-review`. The framebuffer excludes the native caption, so caption tinting, real icon extraction in the running app and Windows 10 fallback are not covered by it. It has no watcher/provider and writes no configuration or recovery. It is intended for explicit visual review, not a batch of ignored tests. This is not physical multi-monitor, screen-reader or live provider acceptance.
